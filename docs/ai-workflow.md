# AI 와 함께 만든 방식

mini-redis 는 AI 에이전트(Claude Code)가 구현을 주도했다. 이 문서는 "AI 로 짰다"가 아니라 **AI 가 틀려도 잡히는 구조를 어떻게 만들고, 무엇이 실제로 잡혔는지**를 적는다.

## mini-react 에서 바꾼 것

mini-react 는 테스트 작성 → 구현 → 병렬 리뷰를 전부 에이전트 파이프라인에 맡겼다. 품질 지표는 좋았지만, 끝나고 보니 **사람의 머리에 남은 것이 없었다.** 그래서 mini-redis 는 순서를 바꿨다.

| 단계 | 사람 | AI |
|---|---|---|
| 개념 | 질문에 자기 말로 답함 (틀린 답도 기록) | 바로 설명하지 않고 질문, 답을 평가하고 바로잡음 |
| 설계 | 결정에 참여 (만료 시각 저장 위치, eviction 정책, API 방식 등) | 선택지·트레이드오프·추천 |
| 구현 | 확인 | 계약(헤더) → 테스트(실패 확인) → 구현 |

## 결함을 잡는 장치를 여러 겹으로

| 장치 | 무엇을 보나 | 실제로 잡은 것 |
|---|---|---|
| 테스트 먼저 + 편집 후 자동 테스트 (hook, WSL `make test`) | 고친 즉시 빌드·테스트 | `make asan` 목적 파일이 일반 빌드에 섞여 링크 실패하던 Makefile 결함 |
| 테스트 설계 단계 | 모듈 사이 계약 | `KEYS` 가 순회 중에 main 테이블을 조회하면 rehash 가 진행돼 순회 계약을 어김 → expires 만 보는 함수로 바꿈 |
| AddressSanitizer + UBSan (CI) | 메모리 오류 | (지금까지 0건) |
| 진짜 클라이언트 연기 시험 | 호환성 | `redis-cli --pipe` 가 끝 확인용으로 보내는 `ECHO` 누락 |
| **차등 테스트** (진짜 Redis 와 응답 비교) | 기대값 자체가 맞는지 | 배열 원소 수 상한을 AI 가 옛 Redis 값(1,048,576)으로 기억해 설계·코드·단위 테스트에 같이 적은 오류 |
| **사람의 개념 질문** | "정상 사용" 밖의 관점 | "epoll 도 굶주림에서 완전히 자유롭지는 않을 것 같다" → 쏟아붓는 클라이언트 옆 PING 763ms 재현 → 1ms |
| 벤치마크 | 수치가 이상한지 | 데모 API p99 1005ms = TCP SYN 재전송 1초 → HTTP 서버 연결 대기열 5 가 원인 |

어느 장치 하나만으로는 위 결함을 다 잡지 못했다. 특히 마지막 세 개는 단위 테스트가 전부 통과한 상태에서 나왔다.

## 측정

| 모듈 | 테스트 | 첫 시도 |
|---|---|---|
| 해시 테이블 | 24 | 16/16 → 추가 8 중 7 (1건은 테스트 설계 오류) |
| 버퍼 · RESP | 6 + 18 | 통과 |
| 키 공간 · 만료 | 17 + 6 | 통과 |
| 명령 | 14 | 통과 |
| 서버 통합 | 6 | 4/6 (실패 2 = 질문에서 찾은 결함) |
| 차등 | 2129 비교 | 3 불일치 (테스트 설계 2, AI 사실 오류 1) |
| 데모 기능 | 8 | 통과 |

한계: 테스트와 구현을 같은 세션이 썼다. 같은 맹점을 공유할 수 있어서, 첫 시도 통과보다 **차등 테스트와 사람의 질문이 무엇을 찾았는지**를 더 중요하게 본다.
